# Что осталось после ветки `feat/install-choices`

Ветка добавляет в установку офлайн-бандла выбор окружения (demo/prod), моковых данных, домена и режима TLS, шрифтов,
скрипт смены адреса и ряд исправлений, найденных при установке на `lct.velikoss.ru`. Всё ниже не сделано или требует
решения. Разделы упорядочены по важности.

## Что сделано в ветке (для контекста)

| Что | Где |
|---|---|
| `install.sh` спрашивает окружение, адрес, режим TLS, шрифты, моковые данные; сводка и подтверждение; предполётные проверки публичных режимов (порты, DNS, Let's Encrypt, ufw) | `scripts/bundle_install.sh` |
| Режимы TLS `off` / `internal` / `acme`: HTTPS на 443, Let's Encrypt, S3 по https, plain-http только на loopback | `compose/Caddyfile`, `compose/docker-compose.yml`, `scripts/gen_env.sh`, `scripts/lib_host.sh` |
| Смена адреса и режима у установленного стенда, включая адреса клиента `crm-bff` в БД Keycloak | `scripts/set_host.sh` |
| Моковые данные в бандле: три сида в контейнере node, `seed_demo.sh`, образ `seed-demo` в `images.yaml` | `seed/`, `scripts/seed_demo.sh`, `scripts/sync_seed.sh` |
| Шрифты Rostelecom Basis: необязательный каталог, `--fonts` при сборке бандла и установке, 404 вместо HTML-заглушки | `compose/fonts/`, `scripts/build_offline_bundle.sh`, `Caddyfile` |
| Исправлены: админ Keycloak 25 (`KEYCLOAK_ADMIN*`), предвыделение 20–36 ГБ в SeaweedFS, CSP блокировала inline-скрипты страницы входа Keycloak | `compose/docker-compose.yml`, Helm-чарт, `Caddyfile` |

Проверено на сервере с настоящими образами: сквозная установка `--tls off` (smoke 9/9, сиды, шрифты), `--tls internal` на нестандартных хост-портах
(https, редирект, S3, сиды), `set_host.sh` (новый адрес до правки 400, после 302), админ Keycloak (0 пользователей до обновления compose, 1 после, вход проходит),
отказ предполётной проверки на занятых 80/443.

## 1. Привести боевую VM к управляемой конфигурации (lct.velikoss.ru)

Стенд там собран вручную (правки `Caddyfile`, compose и `.env` руками, файлы лежат в каталоге распакованного бандла v0.2.0). Он работает, но не совпадает с репозиторием.

- [ ] Обновить на VM `compose/docker-compose.yml`, `compose/Caddyfile`, `compose/.env.example`, каталог `scripts/`, `seed/` из этой ветки (или поставить новый бандл рядом).
- [ ] Выполнить `bash scripts/set_host.sh --host lct.velikoss.ru --tls acme`. Он допишет в `.env` переменные режима, пересоздаст caddy/api/worker/web/keycloak. Сертификат Let's Encrypt лежит в томе `rtk-crm_caddy_data` и сохранится. Ожидаемый простой 1–2 минуты.
- [ ] После пересоздания keycloak в master realm появится администратор (пароль в `.env`: `KEYCLOAK_ADMIN_PASSWORD`), проверить вход в консоль.
- [ ] Освободить место: том `rtk-crm_seaweed_data` занимает ~22 ГБ предвыделенных файлов. Для демо проще пересоздать том и заново залить данные: `docker compose … down`, `docker volume rm rtk-crm_seaweed_data`, `up -d --wait`, `bash scripts/seed_demo.sh` (загруженные файлы, в том числе реестр ЕГРЮЛ, зальются заново).
- [ ] Положить шрифты в `compose/fonts/` (каталог смонтирован, перезапуск не нужен).
- [ ] Решить судьбу демо-режима на публичном адресе (п. 6).

## 2. Влить изменения в репозиторий backend

Копия `Caddyfile` в `backend/deploy/` обязана совпадать с `deploy/compose/Caddyfile` побайтно, иначе job `drift` в CI (`check_drift.py --backend-dir`) краснеет. В рабочем дереве backend уже лежат правки, но не закоммичены:

- [ ] `backend/deploy/Caddyfile`: та же версия, что в deploy (по умолчанию поведение локальной разработки не меняется: проверено `caddy adapt` при пустом окружении).
- [ ] `backend/docker-compose.yml`: `KEYCLOAK_ADMIN`/`KEYCLOAK_ADMIN_PASSWORD` для Keycloak 25 и `-master.volumePreallocate=false` для SeaweedFS.

Порядок: PR в backend и PR в deploy идут вместе.

## 3. Прогнать путь ACME на свободной машине

Выпуск сертификата Let's Encrypt установщиком «с нуля» в этой ветке не проверялся: на тестовой VM порты 80/443 заняты живым стендом. Проверено косвенно: конфигурация Caddy для `acme` адаптируется и содержит issuer `acme`, а тот же Caddy с аналогичной конфигурацией уже выпустил сертификат на боевой VM, режим `internal` проверен на реальных образах.

- [ ] Свободная VM с DNS-записью: `bash install.sh --profile demo --host <домен> --tls acme`, убедиться, что сертификат выпустился, `smoke.sh https://<домен>` зелёный, редирект http→https работает.
- [ ] Прогнать `set_host.sh` в публичном режиме (`off` → `acme`, `acme` → `internal`): в этой ветке проверен только внутри режима `off`.

## 5. Шрифты в релизном бандле

Релиз из CI (`release.yml`) собирает бандл без шрифтов: они лицензионные и не в git. Нужно решение, откуда CI берёт файлы (приватный релиз-ассет или секрет-архив), и вызов `build_offline_bundle.sh … --fonts <каталог>`. До этого шрифты передаются при установке (`--fonts`) или кладутся в `compose/fonts/`.

## 6. Безопасность демо-режима на публичном адресе

- [ ] Экран входа и `/config.json` в demo публикуют демо-логины и секрет клиента `crm-bff`, любой посетитель `lct.velikoss.ru` входит администратором. Установщик предупреждает, но не запрещает. Варианты: закрыть демо-стенд по IP или basic-auth в Caddy, или перевести боевой домен на `--profile prod`.
- [ ] После `set_host.sh` старые адреса (`redirect_uris`, `web_origins`) остаются допустимыми для клиента. Убрать в консоли Keycloak или научить скрипт удалять адреса прежнего хоста.
- [ ] В режиме `internal` S3-прокси (`:8333`) тоже на https с самоподписанным сертификатом: клиент должен доверять корневому сертификату Caddy (установщик печатает команду), иначе загрузка файлов из браузера не пройдёт.
